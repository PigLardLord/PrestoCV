# Packages and targets

This is the authoritative list of production modules and of what each may import. The checker's `rules.json` must agree with it in both directions ([ADR 0006](adr/0006-enforce-architecture-mechanically.md)):

- every target listed here has a rule, or is declared `notYetImplemented`;
- no rule allows an import this file does not allow. Rules may be stricter, never looser;
- every dependency declared in a `Package.swift` must be an allowed import.

A new target, or a new edge between targets, changes this file in the same pull request.

Notation:
- **May import** lists every module the target may `import`. Swift and Foundation are always allowed; in domain targets only as value types (R2).
- The platform column reads iOS / macOS / Linux / Android. **Linux ✓** means the target must build and pass its tests on Linux in CI. **Android ✓** means it must also build for Android (arm64, API level 28) in CI; its tests do not run there yet ([ADR 0026](adr/0026-keep-the-core-portable-to-android.md)).

Test targets and test-support targets are described below each package. The checker applies only its import allow-lists to them.

## Package `DiagnosticLogging` — Diagnostic logging

| Target | Layer | Platforms | May import |
|---|---|---|---|
| `DiagnosticLogging` | port, value types and decorators | iOS, macOS, Linux ✓, Android ✓ | Foundation |
| `DiagnosticLoggingOSLog` | outbound adapter | iOS, macOS | `DiagnosticLogging`, `os` |

A leaf package that depends on no other package ([ADR 0030](adr/0030-log-through-one-interface-that-carries-no-cv-content.md)). `PrestoCVCore`, `CVPDFExporter` and `CVGeneratorAI` may depend on its `DiagnosticLogging` target, and only on that one: an exception to the forbidden edges between the three packages, as `DiagnosticTrace` is.

**`DiagnosticLogging`**
- **The port, `DiagnosticLogger`:** one synchronous `log(_:)` that never throws, with the shorthands `debug`, `info`, `notice`, `error` and `fault`.
- **The entry, `LogEntry`:** a level, a `LogCategory` each module declares once, an event that is a `StaticString`, and fields of a closed set of kinds: `count`, `duration`, `flag`, `token` (a `StaticString`), `identifier` (a UUID) and `error`, which is written as its type and the `logCode` of a `LoggableError`, never as its description. So no value of a CV can reach a line. `line` writes the event and its `key=value` pairs.
- **The decorators:** `FanOutLogger`, `MinimumLevelLogger` and `SilentLogger`, for previews.
- **`Stopwatch`:** the time a step took, on an injected `Clock`.
- No platform condition, no Apple-only import, no bundle (R11, R18).

**`DiagnosticLoggingOSLog`** writes each entry to the unified log: one `os.Logger` per category of the subsystem, the levels mapped one to one, and the line as public text. Only the composition root makes one (R4). Every file is wrapped in `#if canImport(os)`.

**Test support and tests.**
- `DiagnosticLoggingTestSupport` may import `DiagnosticLogging`, Foundation, Synchronization. It holds `RecordingLogger`, which records the entries under a `Mutex`, and `TickingClock`, a `Clock` that moves on by one step at every reading.
- **`DiagnosticLoggingTests`** may import `DiagnosticLogging`, `DiagnosticLoggingTestSupport`, Testing, Foundation. They test the lines, the decorators and the stopwatch, on Linux too.
- **`DiagnosticLoggingOSLogTests`** (Apple hosts) may import `DiagnosticLoggingOSLog`, `DiagnosticLogging`, Testing and `os`.

## Package `DiagnosticTrace` — Trace of a test build

| Target | Layer | Platforms | May import |
|---|---|---|---|
| `DiagnosticTrace` | port, value types, decorators and rules | iOS, macOS, Linux ✓, Android ✓ | `DiagnosticLogging`, Foundation, Synchronization |
| `DiagnosticTraceFiles` | outbound adapter (the store) | iOS, macOS, Linux ✓ | `DiagnosticTrace`, `DiagnosticLogging`, Foundation, Synchronization |
| `DiagnosticTraceDistribution` | outbound adapter (how the app was installed) | iOS, macOS | `DiagnosticTrace`, StoreKit |

Each step of the AI draft and of the import, with the text it read and wrote, kept on the device in TestFlight and Debug builds only ([ADR 0032](adr/0032-record-each-step-of-the-ai-draft-and-the-import-in-test-builds.md)). It carries CV content, so it is a package of its own, apart from `DiagnosticLogging`, which never does. It depends on `DiagnosticLogging` only. `PrestoCVCore` and `CVGeneratorAI` may depend on its `DiagnosticTrace` target, and only on that one; only the composition root imports its adapters and makes its recorder, gate and decorators, which the checker's `compositionOnly` rule enforces.

**`DiagnosticTrace`**
- **The port, `DiagnosticTracer`:** `begin(kind)` opens a run of a kind (`aiDraft` or `textImport`) and returns its `TraceRunRecording`, which records steps and finishes with an outcome; `record(_:_:into:)` adds a step to the run whose `TraceScope` the work is in (`within` sets it: the run, `suppressed` or none; a step outside a run is dropped); `mirror(_:)` takes a log entry. Every call is synchronous and never throws.
- **The values:** `TraceRun` (id, kind, start, build, steps, outcome), `TraceStep` (sequence, elapsed time, a `TraceStepName` from a closed set, ordered fields) and `TraceField`, whose `TraceValue` is a text cut at 32 KB, a count, a flag, a duration or a token.
- **The decorators:** `NoTracer`, for previews and tests that do not look at the trace; `GatedTracer(gate:next:)`, which drops what comes while its gate is closed; `TracingLogger(tracer:next:kinds:)`, a `DiagnosticLogger` that mirrors each entry into the run of the work's scope, or into the session events when the work is in no run.
- **The recorder, `TraceRecorder`:** keeps each open run under its size cap and hands every new state to a `TraceStoring`, on an injected clock, time source and id generator (R2).
- **The gate rule:** `ConstantGate` for a Debug build, and `DistributionGate`, open only for a verified TestFlight install (`DistributionAnswer.sandbox`) through the port `DistributionReading`; everything else fails closed.
- **The rules of the files:** the JSON document of a run (schema 1, keys sorted), its plain-text summary (`TraceSummary`), the ten runs kept (`TraceRetention`), the 200 session events kept (`TraceSessionLog`), the port `TraceReading`, through which the diagnostics screen lists and shares the runs, and the port `TraceSharing`, which makes and discards the copies of one holder (an id the caller picks, one per screen).
- No platform condition, no Apple-only import, no bundle (R11, R18).

**`DiagnosticTraceFiles`** is the store, `TraceFileStore`: one folder, made on the first write, excluded from backup, with files under complete protection on iOS; per run a JSON document and a summary; the session's events. It writes on one task off the main actor, only the latest state of each run, and logs a failure through `DiagnosticLogger` under the category `trace`. It makes the copies to share in a temporary folder, each holder's in a folder of its own and the single set of `TraceReading` in one more, so that one holder's copies and discard never touch another's; it removes them all at start and on a purge.

**`DiagnosticTraceDistribution`** reads `AppTransaction.shared`, never `refresh()`, and maps its environment to a `DistributionAnswer`. Every file is wrapped in `#if canImport(StoreKit)`, and the manifest adds the target on Apple hosts only.

**Test support and tests.**
- `DiagnosticTraceTestSupport` may import `DiagnosticTrace`, Foundation, Synchronization. It holds `RecordingTraceStore`, `RecordingTracer` (the real recorder on a stopped clock, with the runs it recorded), `FixedDistribution` and `StoppedClock`.
- **`DiagnosticTraceTests`** may import `DiagnosticTrace`, `DiagnosticTraceTestSupport`, `DiagnosticLogging`, `DiagnosticLoggingTestSupport`, Testing, Foundation. They test the recorder, the gate's truth table, the decorators, the document, the summary and the retention, on Linux too.
- **`DiagnosticTraceFilesTests`** may import `DiagnosticTraceFiles`, `DiagnosticTrace`, `DiagnosticLogging`, `DiagnosticLoggingTestSupport`, Testing, Foundation, Synchronization. They write to a temporary folder, on Linux too; a spy of the folder protection records its calls under a `Mutex`.

## Package `PrestoCVCore` — CV Authoring and CV Import

| Target | Layer | Platforms | May import |
|---|---|---|---|
| `PrestoCVDomain` | domain | iOS, macOS, Linux ✓, Android ✓ | Foundation |
| `PrestoCVApplication` | application | iOS, macOS, Linux ✓, Android ✓ | `PrestoCVDomain`, Foundation |
| `PrestoCVPersistence` | outbound adapter | iOS, macOS, Linux ✓, Android ✓ | `PrestoCVApplication`, `PrestoCVDomain`, Foundation, Glibc, Darwin, Android |
| `PrestoCVImporting` | domain + application (CV Import) | iOS, macOS, Linux ✓, Android ✓ | `PrestoCVDomain`, `DiagnosticLogging`, `DiagnosticTrace`, Foundation |
| `PrestoCVImportingPDFKit` | outbound adapter | iOS, macOS | `PrestoCVImporting`, `DiagnosticLogging`, PDFKit, UIKit, AppKit, CoreGraphics, Foundation |
| `PrestoCVApplicationNaturalLanguage` | outbound adapter | iOS, macOS | `PrestoCVApplication`, `PrestoCVDomain`, NaturalLanguage, Foundation |

**`PrestoCVDomain`**
- **`CV`**, the aggregate:
  - a typed identity (`CVID`);
  - `revision`, `createdAt` and `updatedAt`, settable only inside the package;
  - a private title, `PersonalDetails`, and ordered sections of entries;
  - the "has enough content to be saved" rule, `SaveRule`: a detail of the person is written, or a section has an entry. It reads plain values, so the legacy app's editor is judged by it too ([ADR 0025](adr/0025-hold-the-legacy-app-to-the-separation-rules.md));
  - duplication with a title composed by the caller.
- **`TextRules`**, the one rule for the text of a CV, applied by the initialisers and setters of every value type that holds text, so also by the store's reader and the draft mapper (R8). It removes without a word, in single-line and multi-line text alike: control characters other than line breaks (NUL and DEL included), bidirectional embeddings, overrides and isolates (U+202A to U+202E, U+2066 to U+2069), the marks U+200E, U+200F and U+061C, and tag characters (U+E0000 to U+E007F). A line break or tab in a single-line field becomes a space; a multi-line field (the summary, and the description of an experience, an education and a certification) keeps LF only: CRLF, CR, NEL, VT, FF, U+2028 and U+2029 become LF, a tab a space. ZWJ and ZWNJ are kept, and so are U+200B, U+2060, U+FEFF and U+00AD. A tag-sequence flag emoji (England, Scotland, Wales) loses its tags. The table is in the doc comment of `TextRules`; a test lists every text field by reflection, so a new one cannot skip the rule. The list of interests has one rule too, `CVSections.canonicalInterests(_:cleaningText:)` (trimmed, none empty, no two equal ignoring case): `setInterests` applies it with the cleanup, and the store's reader applies it without, to tell a canonical stored list from a corrupt one before the cleanup changes it.
- **`CVLimits`** and **`SaveVerdict`**: each text at most 16,384 UTF-8 bytes and 10,000 characters, all texts together at most 262,144 bytes, each section at most 200 entries. `CV.saveCheck()` says `ok`, `notEnoughContent`, `textTooLong(field)`, `tooManyEntries(section)` or `cvTooLarge`, and `canBeSaved` means `ok`. The limits equal or sit below the exporter's document validator, which the domain cannot import (R1), so a CV that can be saved maps to a document the validator accepts. A stored CV above a limit still opens, and is never cut; saving it is refused with the reason (`AuthoringError.textTooLong`, `.tooManyEntries`, `.cvTooLarge`).
- **Value objects:**
  - `PartialDate` (year or month precision, partial order);
  - `Period`, whose end is a date, "current" or "ended, date unknown" (`PeriodEnd.unknown`);
  - `SkillLevel` (1–5);
  - `LanguageProficiency` (CEFR + native);
  - `EmailAddress`, `PhoneNumber`, `WebLink`, `DocumentLanguage`, `DesignChoice`.
- **`Period.make(start:end:current:)`** is the single rule that turns loose data into a period, or into a typed `PeriodError`. **`Period.reading(start:end:current:)`** is the same rule for the text of a form (`PartialDate(reading:)` reads "2020" or "2020-05"; any other text is `PeriodError.invalidDate`), and `PartialDate.text`, `Period.startText`, `Period.endText` and `Period.isCurrent` write it back.
- **`FieldCheck`**: whether the text of an e-mail, phone or web-address field reads as one. E-mail addresses and web addresses are judged by `EmailAddress` and `WebLink`; a phone number needs a digit, and is otherwise written as the person likes. The legacy app's editor checks a field when the person leaves it.
- **`CVTitle`**: what a CV is called wherever it is named: its name, otherwise the name of its person, otherwise the role it is for; "Untitled CV", which the app words, only for a CV with none of the three; the name of a copy, that title followed by the app's word for a copy; and the labels of a list's rows, in which a CV whose title reads like another's takes the first number that gives a label no other row shows, so that no two rows read the same. A CV with none of the three, as a new one the editor stored before it was named, is numbered as the platform numbers an untitled document: "Untitled CV", "Untitled CV 2". The legacy app passes the name of a copy to the legacy duplicate operation.
- **`CVSubtitle`**: the line under the title of a CV in a row of the list, which never repeats the title: the name of the person and the role under a CV titled by its own name, only the role under one titled by its person, only the person under one titled by its role; an empty part leaves no separator.
- **`ExampleDraft`**: the fields (`CVField`) a draft started from an example leaves blank, who its person is and how to reach them.
- **`PDFFileName`**: the title of an exported PDF and the name of its file, from the person's name or the CV's, cleaned for every file system and cut to its bytes, around the pattern of the PDF's language, which the app gives from its catalog.
- **`ExportReadiness`**: whether a CV can be exported, and which field to fix: only the person's name is required; a missing e-mail address or phone number only warns.
- **`ExportPolicy`**: the page of version 1's export, A4 with a 43-point margin and 10 pages at most.
- The legacy app reads both while it exports through the legacy exporter; at migration step 5 the policy of `CVRendering` replaces them ([ADR 0025](adr/0025-hold-the-legacy-app-to-the-separation-rules.md)).
- Planned: projects (#54), photo (#53).

**`PrestoCVApplication`**
- **Ports:**
  - `CVRepository`: create, conditional update, load, list, conditional delete. Typed `RepositoryError`, not cancellable.
  - `CVStoreMaintenance`: list the quarantine, restore from it, erase every copy of a CV, purge the quarantine, erase everything. Its use cases are `ReviewStoreIssues`, `RestoreQuarantinedCV`, `EraseCV`, `PurgeExpiredQuarantine` (30 days, from the injected `TimeSource`) and `EraseEverything`, with a typed `MaintenanceError` and an `EraseEverythingOutcome` that names a file by kind and name, never by path.
  - `SampleCVSource`, `IDGenerator`, `TimeSource`. `TimeSource` is so named to avoid shadowing `Swift.Clock`.
  - `TextLanguageReading`: which language a text is written in, as a recognizer reads it (`LanguageReading`: the language it finds on its own, and how likely each language it is given is).
- **Use cases:**
  - `NewCV`, `SaveCV` (create or conditional update, errors translated to `AuthoringError`, including `tooLarge`), `LoadCV`;
  - list (by last change), rename, duplicate, delete, start from a sample, determine onboarding;
  - `ChangeStoredCV`: renames a stored CV (trimmed, never blank), sets the language of its PDF, or changes the parts of its look that the person chose (`LookChange`: the parts chosen, and the look the export sheet showed; the others stay as the store holds them), reading it again just before it is stored, so nothing else changes; a look the stored CV has already is no change and stores nothing. It works through the `StoredCVs` port, generic over the store's own CV, which the legacy app implements over its stored CVs until the migration replaces them ([ADR 0025](adr/0025-hold-the-legacy-app-to-the-separation-rules.md)).
  - `ChangeCV`: changes the look (`LookChange.applying(to:)`: the parts chosen are the shown ones, the others stay as the CV holds them, an id the app does not know included; a CV with no look takes all of the shown one) or the document language of a `CV` and saves it through `SaveCV`, so it is a conditional update: a stale CV is a conflict. A change that leaves the CV as it is writes nothing. It stores the choice and does not check that the design exists. `RenameCV` trims the title.
  - `DetectDocumentLanguage` (#407): the language a CV's own words are written in, among the languages its PDF can be written in. It reads the summary, the professional title, and the roles, degrees and descriptions of the entries, never a name (the person's, an employer's, a school's, a place's); fewer than 15 words tell no language, and only the first 1,000 characters are read. A language is told only when the recognizer finds it on its own, it is one of those offered, its likelihood is at least 0.8, and no other is as likely; otherwise there is none, and the caller decides.
- **`ImportLegacyStore`**: the one-time import of the released app's store ([ADR 0022](adr/0022-ship-legacy-app-as-v1.md)). It reads the candidates of a `LegacyStore` port and hands each CV to a `LegacyImportTarget` port, which stores it as revision 1 with the times it carried, or answers `existing` when the store already holds that id. A source file is removed only after its copy is stored and reads back as what was mapped, and only while it still holds the exact bytes the run read (`LegacyRecord.Version`; the store compares the bytes and answers `LegacyRemoval`: removed, already gone, or changed, in which case the file stays and the report says `sourceChanged`); with removal off, never; a file that fails stays, byte for byte, and the `LegacyImportReport` says which and why (a code, never content), together with what was dropped per CV (`LegacyDrop`) and what each CV keeps in another place for the person to check (`LegacyCheck`: a period that is not a clear range, kept as written in its entry's description; reported apart, as `checks`, never a loss), also for a CV an earlier run stored, since that run may have stopped before its report. The source of a CV with drops or checks is the durable record of what the person must be told: `run` keeps it and lists it as awaiting acknowledgement, and `acknowledgeLosses(of:)` removes it, under the same bytes check, once the person has seen the losses (a source that changed since stays, and the next run reports its new losses) (a run that stops before then finds the CV stored and reports the same drops again). A second run changes nothing in the store. Before it reads the source, the run takes an `ImportTicket` from the target (`beginImport`: the store's erase generation), and the target stores nothing under a ticket that an erase has made old (`Adoption.storeErased`): the run then stops, keeps every source and reports only `storeErased`, so a CV read before an erase never comes back after it, even from another instance of the store. `LegacyImportFailure.Reason.leftOut` sorts the reasons a CV stayed out into the causes the person can act on (`LegacyLeftOut`: `damaged`, the file stays; `notSaved`, the next launch tries again; the others, such as a source that changed after its CV was stored, leave no CV out). `LegacyImportOutcome.mayLeaveCVsOut` is true when old CVs may be missing from the store: some were left out, or the run failed before it read them.
- **Listing** returns the healthy CVs plus `StoreIssue`s: `corrupt`, `upgradeRequired`, `unreadable`, `tooLarge`, `quarantineFailed`.
- **`Autosave`**: when an editor writes what it shows. A second after the last change, at once on a flush (the app leaving the foreground, the editor being left); never when the content equals what is stored, so its edit time stays; a CV the store does not hold yet only once it is worth storing. After each write the content is compared with the store again: a change made while it ran, or one that undid it, is written next, and a flush goes on until the store holds what the form shows. A failed write leaves the content in memory and a `failed` status until a write succeeds or the content returns to what the store holds, and a write that runs meanwhile says `retrying`, not `writing`, so that it hides no failure (`hasUnresolvedFailure`); the error the write threw goes to a hook the caller gives (`onWriteFailure`), apart from the status. The store is known to hold the content (`storeHoldsTheContent`) only when no write runs and nothing differs: the end of a write that runs can leave something else there. A write the store cancels is no failure: the content stays to be written, and the flush passes the cancellation on. The write is told whether the store holds the CV, so that it needs nothing of the editor; it and the clock are given by the caller.

**`PrestoCVPersistence`**
- `FileCVRepository`:
  - one `CVFileV1` file per CV, named from its id;
  - atomic writes, with `complete` protection unless the composition root gives another class through `StoreOptions` (tests of the store's logic give none; [ADR 0009](adr/0009-persisted-schema-v1.md): what that means for a locked device and for CI hosts), and a read-back check before every write;
  - a failed write, delete, restore, erase or purge (the failures mapped to `writeFailed`) keeps the error it came from, as a `FailureCause` (domain, code, and the `errno` under a Cocoa error); the classified read, lock, listing and quarantine outcomes keep no cause, and the use cases drop it when they translate to `AuthoringError`;
  - every mutation under an exclusive `flock` on the store, from the C library of the platform: `Glibc`, `Darwin` or `Android` ([ADR 0026](adr/0026-keep-the-core-portable-to-android.md)); while the lock is held elsewhere the call suspends between attempts, and it ends in `storeUnavailable(.lockTimeout)` at the deadline of `StoreOptions.lockWait` ([ADR 0009](adr/0009-persisted-schema-v1.md));
  - reads classified as described in R12;
  - `Quarantine/` with validated restore, erase and purge, and `eraseAll` (in `FileCVRepository+Maintenance.swift`), which under one hold of the lock first moves the store's erase generation (`.erase-generation`, one byte per erase; if it cannot, nothing is removed) and then removes every CV file, the quarantine and the staged copies, and the ledger unless the caller keeps it (it does while a legacy source remains, so that source is not imported again; a kept ledger is named in the report), and names in its report any file it could not remove.
- `DirectoryLegacyStore` and `FileCVRepository.adopt`: the adapters of the legacy import. The directory store lists `cv_*.json`, reads only regular files within a size cap and never through a link (R8), and maps each through `LegacyCVFile` (the legacy shape, read as the released app reads it, with the look mapped as ADR 0022 says) to a domain CV; `LegacyPeriod` converts the period text only when it is an unambiguous range of two dates, and drops the rest. `beginImport` reads the erase generation under the lock; `adopt` runs under the store lock, stores nothing when the generation moved since the ticket, and keeps the legacy times, which `create` would reset; a legacy file is never read as schema 1, because the store lists only `*.cv.json`.
- `DirectorySampleCVSource`: sample CVs from an injected directory, in the same v1 format and through the store's own reader. They are kept in `PrestoCV/Resources/Samples/`, and the app ships them from the switch to the new stack on (version 1 ships the legacy samples).

**`PrestoCVImporting`** turns a CV someone already has into a draft, with rules only ([ADR 0027](adr/0027-import-a-cv-from-its-text-with-rules.md)). It is the CV Import context, packaged with Authoring because it reads Authoring's value objects and period rule instead of copying them: the only edge between two contexts inside this package, and it goes one way.
- **What a reader saw, `ExtractedLayout`:** the lines of a pasted text, or the words of each page of a PDF with their box and style. Untrusted input (R8), bounded by `ImportLimits`.
- **The document in reading order, `SourceDocument`:** blocks (a line, a heading, a list item, a row of cells) with page, box, column and style when there are any, over one canonical text. `SourceSpan`s count Unicode scalars.
- **The rules:**
  - `PlainTextReader` for pasted text, and `LayoutAnalyzer` for pages: lines, cells, a sidebar told from a table, the reading order, repeated headers and footers, page numbers;
  - normalisation: chat Markdown and chatter, ligatures, line-end hyphenation, icon glyphs;
  - `SectionVocabulary` and the segmentation by headings in six languages, Europass and Lebenslauf labels included;
  - the readers of names, contacts, dates and periods, entries, skills, languages and levels, certifications and interests.
- **The draft, `ImportedCV`:** every value is `Sourced`, with the spans it quotes and the rule that read it, if any. Values the rules are unsure of carry a check reason, and the review list collects them. Text that fits no field is kept as text not imported; noise is left out with its reason. A final gate checks every value against its spans.
- **The use case, `ImportCV`:** pasted text, or a PDF through the port **`PDFTextExtracting`**; both are untyped `throws` and cancellable, and both are read within one budget of work. Typed `ImportError`: empty, too large, too many pages, encrypted, unreadable, no text (a scan).
- **What it logs** through the `DiagnosticLogger` its initialiser takes ([ADR 0030](adr/0030-log-through-one-interface-that-carries-no-cv-content.md)), under the category `import`: the kind of input, its pages and characters, the sections by kind and the time taken; the headings not recognised and the lines left unplaced, as counts; a failure by kind, and the limit of the bounded reading it reached; a cancellation.
- No platform condition, no Apple-only import, no bundle (R11, R18). It is built for Android with the rest of `PrestoCVCore`.

**`PrestoCVImportingPDFKit`** implements `PDFTextExtracting` with PDFKit: each page's words with their box, font size and weight, in PDFKit's order, and nothing decided about the reading order, which the core decides. It checks the size, the page count and the encryption before it reads any text, refuses a page whose text is longer than the characters left before it reads the page's glyphs, counts the words as it reads them, and stops in the middle of a page once its task is cancelled. A word whose font PDFKit cannot name comes back without its weight, so the adapter draws the page with CoreGraphics and marks a word bold when its strokes are clearly heavier than the page's ([ADR 0027](adr/0027-import-a-cv-from-its-text-with-rules.md)). `characterBounds(at:)` has no box for the line breaks of `PDFPage.string`, so the adapter walks the two together. Through the logger its initialiser takes, it logs the pages and the words it read, and the limit that stopped it, which it throws as a `LimitReached` for the use case to word and log. Every file is wrapped in `#if canImport(PDFKit)`.

**`PrestoCVApplicationNaturalLanguage`** implements `TextLanguageReading` with the system's `NLLanguageRecognizer` (#407). It reads the text twice: once among every language the recognizer knows, for the language it finds on its own, and once among the languages it is given only, for the likelihood of each. A language is given by its tag, as the recognizer names languages; a tag it does not know gets no likelihood, and a text it calls undetermined has no language. The rule that decides is `DetectDocumentLanguage`, in the core. Every file is wrapped in `#if canImport(NaturalLanguage)`.

**Test support and tests.**

It holds the unit tests of every rule and the **contract table**: the synthetic corpus under `PrestoCVCore/Tests/ImportFixtures/` (texts, recorded page layouts and their PDFs, each with the fields it states), measured per language and form, and checked line by line: every line of every fixture is covered by a value, a text not imported or a left-out piece. No real CV is ever committed.
- **`PrestoCVImportingPDFKitTests`** (Apple hosts) may import `PrestoCVImportingPDFKit`, `PrestoCVImporting`, `DiagnosticLogging`, `DiagnosticLoggingTestSupport`, `DiagnosticTrace` (its `NoTracer`), Testing, Foundation, PDFKit, CoreGraphics, and CoreText, with which it draws hostile pages when it runs. Its contract test reads the fixture PDFs with PDFKit and compares the words with the recorded layouts that the Linux tests use.
- **`PrestoCVApplicationNaturalLanguageTests`** (Apple hosts) may import `PrestoCVApplicationNaturalLanguage`, `PrestoCVApplication`, `PrestoCVDomain`, Testing, Foundation and NaturalLanguage. They run the system's recognizer on texts of work in the languages of the PDF, and through `DetectDocumentLanguage`.
- `PrestoCVImportingTestSupport` may import `PrestoCVImporting`, `PrestoCVDomain`, Foundation. `ImportFixture` builds an `ImportedCV` and an `ImportResult` that no reader read, each value quoting a piece of one text, for the tests of what consumes an import. The initialisers it needs are `package`, so that only this package can make a value without its evidence.
- `PrestoCVCoreTestSupport` may import `PrestoCVApplication`, `PrestoCVDomain`, Foundation, Synchronization. It holds:
  - `InMemoryCVRepository`, `SteppingClock`, `SequentialIDGenerator`, and `InMemoryLegacyStore`, the released app's store in memory, for the packages that cannot make a `LegacyRecord` (its key and version are package-only);
  - `ManualClock`, a `Clock` that moves only when a test moves it, for the timing of `Autosave`;
  - the **`CVRepository` contract suite**: round trip with timestamps, create twice, update bumps the revision, stale update and stale delete, 50 concurrent updates from one revision leave exactly one success, update after delete, listing order.
- File-store behaviour that an in-memory store cannot have is tested in the Core tests, not in the contract: mixed directory, unreadable, oversized and hostile files, restore, erase, purge, and two instances racing.

**`CVDocumentModel`**
- **`CVDocument`**, the package's public contract, also the JSON a backend accepts:
  - `schemaVersion` (other versions are rejected) and `language`;
  - the person: name, professional title, email, phone, location, website;
  - typed sections: summary, experience, education, skills, languages, certifications (name, issuer, year, URL, description), profiles, interests;
  - dates as `DocumentDate` and `DocumentPeriod` with `PeriodEnd` `present`, `date` or `unspecified`, never display strings.
- **Explicit JSON.** Sections are `{"kind": …}` objects and periods carry an `end` discriminator.
- **`CVDocumentValidator`** is the anti-corruption layer for documents from outside:
  - it checks the name, counts, dates and ratings;
  - it bounds text in UTF-8 bytes, per field and for the whole document, and refuses control characters and bidirectional overrides;
  - JSON arrives through `decode(json:)`, which checks the size before decoding.
- **The JSON Schema**, version 1, is committed as [cv-document.schema.json](../../CVPDFExporter/Docs/cv-document.schema.json). `DocumentSchemaTests` hold it to the type in both directions: what the type encodes validates, its property names, section kinds and language levels are the schema's, and the bounds both state (years, months, ratings, entry counts) are the validator's. The byte bounds on text stay in the validator, which JSON Schema cannot express.

**`CVDesignCatalog`**
- **`MarkupContract`**, version 1: elements, classes, section kinds, ratings, pseudo-classes. See [markup-contract.md](../../CVPDFExporter/Docs/markup-contract.md).
- **The CSS policy:** a tokenizer, an allow-list of properties and values, and canonical re-serialisation into `ValidatedStylesheet`, whose initialiser is internal.
- **`DesignPackageValidator`** takes raw bytes and returns a `ValidatedDesign`: manifest, stylesheet and PNG preview.
  - The manifest's `name` is one line of 1–80 Unicode scalars that is not only white space, and its `description` has up to 500 scalars and may span lines. Neither holds a control character (the description's new line aside), a line or paragraph separator (U+2028, U+2029) or an explicit bidirectional embedding, override or isolate: `invalidName`, `invalidDescription`. The directional marks U+200E, U+200F and U+061C are allowed. `FileDesignStore` applies the same predicates to the entries of its index.
  - The manifest names the design's default palette and default font scheme by identifier. A missing key, or a value that is not a string, is a malformed manifest; an identifier the catalog does not know is reported (`unknownPalette`, `unknownFontScheme`).
  - The version is `MAJOR.MINOR.PATCH`: each part is `0` or one to nine ASCII digits without a leading zero, so a version has one spelling. `DesignManifest.version` is a `DesignVersion`, stored and decoded as that text and ordered by number (`1.0.10` is later than `1.0.9`). A missing or non-string version is a malformed manifest; a string that is not a version is `invalidVersion`.
  - `claimedIdentifier(in:)` reads the identifier a package claims, without validating the rest, and answers `identifier(id)`, `noIdentifier` (the manifest was read and its `id` is missing, not a string or not a valid identifier: the package can never be installed) or `uninspectable` (over the size cap, or not a JSON object with a `manifest` object: it may name any identifier once it is repaired). The catalog reserves with it the identifiers of the bundled packages (see `InstallDesign`).
  - A violation's description prints at most 64 scalars of the text it names, escaped to ASCII and marked when cut. The violation itself keeps the full text.
- **Customisation values:**
  - `HexColor`, and `Palette`, which exists only with readable contrast;
  - `NamedPalette`: a closed set named after colours, never after a design (`ink`, `slate`, `ocean`, `plum`). Each passes the `Palette` contrast rule, and a test rebuilds every case through the public initialisers. Its raw value is the identifier a design choice stores;
  - `FontScheme`: a closed set of system families (`system`, `serif`, `rounded`), also stored by its raw value.
- **Use cases:**
  - **`ListDesigns`**, **`GetDesign`** and **`ResolveDesign`** use untyped `throws`, as `InstallDesign` does (R7). A `CancellationError` from the store is passed through unchanged. Any other failure of the store is translated to `storeUnavailable`. Their own errors, such as `unknownDesign`, stay as they are;
  - **`ListDesigns`**: the installed designs' manifests, ordered by identifier;
  - **`GetDesign`**: one installed design, or `unknownDesign`;
  - **`ResolveDesign`**: turns a design identifier and optional palette and font scheme identifiers into a `ResolvedDesign` (stylesheet, palette, font scheme). A palette or font scheme that is missing or unknown falls back to the design's default; an unknown design is `unknownDesign`. It takes raw identifiers because the catalog does not import the domain (R1), so `PrestoCVIntegration` maps a CV's `DesignChoice` to them;
  - **`InstallDesign`**: validate the raw bytes, then refuse the identifier of a bundled design, then `DesignRenderingGate.verify`, then `DesignStore.save`, which records the design as `imported`. Nothing is stored unless every check passes. It uses untyped `throws` and passes its errors through, so a cancelled render, source read, origins listing or save ends in a `CancellationError`;
    - **The store has the last word.** The checks below are an early out, before the render. `DesignStore.save` decides under the store's lock, and an import it keeps out (`keptBundled`) is the same `bundledIdentifier` error, so a bundled design that the sync installs while the import renders is still never replaced.
    - **An import that names the identifier of a bundled design is refused** (`DesignCatalogError.bundledIdentifier`), whatever its version and whether or not the sync has installed that design yet. Every identifier in the bundled source is reserved: the same `BundledDesignSource` lists the packages, and `DesignPackageValidator.claimedIdentifier(in:)` reads the identifier each claims without validating the rest, so a bundled package that fails validation still reserves its identifier. A package whose manifest names no valid identifier (`noIdentifier`) reserves nothing. An import is also refused when the store records the identifier as `bundled` (`installedOrigins()`), even if that design has left the bundle: a bundled design is never replaced by an import. A source that cannot be read stops the import (`bundledDesignsUnavailable`), and so does a store that cannot list its origins, since the identifier cannot be judged, or that fails to save the design (`storeUnavailable`). **The reservation fails closed.** A bundled package that cannot be inspected (`uninspectable`: over the validator's cap, not JSON, not a design package) may name any identifier once the bundle is repaired, and an import that took that identifier meanwhile would stay a conflict for good. So it stops every import, not only one of its own identifier, with `bundledPackageUninspectable` and the package's name as the source names it. The bundle is the app's own, so this is a defect of the app, not of the user's import; the sync reports the same package as `rejected`, and once the bundle is repaired it installs the design with no conflict. The package is validated first, so an invalid package is reported as invalid. `InstallDesign` and `SyncBundledDesigns` take validators with one size cap, so one cap decides both which bundled packages the sync installs and which identifiers an import may not take; a test pins that a package within the cap is both installed and reserved, and one over it is rejected by the sync and blocks every import. The composition root builds `SyncBundledDesigns` at launch with the standard `DesignPackageValidator()` (step 5-8c); `InstallDesign` is not built yet, and the step that offers the import of a design builds it with the same validator.
    - **Why refused, and not stored under another identifier:** a CV's design choice names the identifier. An import kept under the bundled identifier shadows the bundled design (a package that claims `modern` at version `999999999.0.0` would block every later fix, and a CV that names `modern` would change appearance without a word). One stored under another identifier would change what the choice names. Refusing is the simplest rule and leaves nothing to reconcile. The user's way out is a package with an identifier of its own.
    - The reverse holds in the sync: a bundled design never replaces an imported one (see `SyncBundledDesigns`).
  - **`SyncBundledDesigns`**: validates each bundled package, then renders it through the same gate, then saves it (R8). It uses untyped `throws`: a `DesignCatalogError` or a `CancellationError`, unchanged.
    - The installed designs and their recorded origins are listed once and compared by manifest version. A package whose identifier no design has is installed, and one newer than the installed design replaces it (upgraded). One of the same or an older version is left alone, neither rendered nor written (adopting a legacy design, below, writes only its record), so a bundled design never downgrades another, and an installed design is read only to adopt it.
    - The save after the render is `DesignStore.saveIfNewer`, which compares again and writes under the store's lock. A design saved by someone else while this one rendered is never overwritten by the older bundled design: the store keeps it and the report lists the identifier as `unchanged`.
    - The sync replaces only designs it installed itself. An installed design whose recorded origin is `imported` holds the identifier of a bundled design: it is left alone, neither rendered nor written, whatever the versions, and the report lists the identifier as `conflicts`. The same happens at the save, which is atomic: `saveIfNewer` keeps an installed design that the store did not record as bundled (an import saved while the design rendered).
    - A design with no recorded origin, one installed before origins were recorded, counts as bundled only if it equals the bundled design: the same identifier, version and content. The sync adopts it: `DesignStore.adoptAsBundled(design)` compares the two under the store's lock (the index's manifest first, then the design's own file, read and validated again), records the origin as `bundled` and changes nothing else, and the report lists the design as `adopted`. The design is not rendered. From then on it is `unchanged` or upgrades like any bundled design. Otherwise it counts as an import, the safe default, and is a conflict. A store that fails to adopt it (an unreadable file, say) reports `failed`; one that no longer adopts it, because an import took it meanwhile, reports a conflict.
    - A package fails on its own, and the others still sync: the validator rejects it (`rejected`, with its name and violations), the gate refuses it or fails (`notRendered`), or the store fails to save it (`failed`).
    - What stops the sync: a store that cannot list its designs (`storeUnavailable`), a source that cannot be read (`bundledDesignsUnavailable`), and cancellation. The sync passes a `CancellationError` through unchanged at every call: the source read, the listing of designs and origins, the adoption, the gate and `saveIfNewer`. The designs saved before it stay saved. The `SyncReport` lists `installed`, `upgraded`, `unchanged`, `rejected`, `notRendered`, `failed`, `adopted` and `conflicts`.
- **Ports:** `DesignStore`, `BundledDesignSource` (raw bytes), and **`DesignRenderingGate`**. A `BundledDesignSource` returns the same packages for the life of the process (the bundled one reads `Bundle.module`, which does not change while the app runs): the import's early refusal of a bundled identifier relies on it, and the store's lock refuses an import over an identifier it records as bundled.
  - `DesignStore` saves, reads one design and lists the manifests, and records each design's origin (`DesignOrigin`: `bundled` or `imported`). `save` is the import's: it records `imported`, and writes nothing and says so (`keptBundled`) when the installed design is recorded as bundled, whatever the versions. `saveIfNewer` is the sync's: it records `bundled`, and saves only when no design has the identifier (`installed`) or the installed one is older (`upgraded`), and otherwise writes nothing: `keptInstalled` when the installed design has the same or a newer version, `keptImported` when the store did not record the installed design as bundled (an import, or a design with no recorded origin, which counts as an import), whatever the versions. The comparison and the write are one step under the store's lock.
  - `installedOrigins()` returns the recorded origins by identifier. A design with no recorded origin, one installed before origins were recorded, is absent from it.
  - `adoptAsBundled(design)` records the installed design as `bundled` when it equals `design` (identifier, version and content) and has no recorded origin. It is one step under the store's lock and changes only that origin. It returns whether the installed design equals `design` and is now recorded as bundled: false when no design has the identifier, the installed one differs in any way, or an import made it.
  - The catalog owns the gate; `CVRendering` implements it, along the allowed Rendering → Catalog edge.

**`CVDesignCatalogFileStore`** holds `FileDesignStore`: the directory is injected, the index is written atomically under a lock (`flock`, from `Glibc`, `Darwin` or `Android`), whose wait suspends and ends in `lockTimeout` at the deadline of the injected `LockWait`, and one instance serves the process. A conditional save compares versions, and checks that the installed design is recorded as bundled, inside the same exclusive lock as the write. Every read validates the file again, so only validated designs leave the store. The index is schema version 2, and each entry's manifest is validated when the index is read; an index of another schema, or with an entry the validator would refuse, is reported and left untouched.

The store also records each design's origin, `bundled` (installed by the catalog's sync) or `imported` (installed by an import), inside the design's own entry of the index. A package is untrusted, so it cannot say what it is: the store records it, outside the package. A save never replaces a design of the other origin, and the store checks that under its lock, in the same step as the write: an import over a design recorded as bundled is refused (`ImportSave.keptBundled`), and a conditional save over one that is not recorded as bundled is kept (`ConditionalSave.keptImported`).
- An index entry is `{"generation":…,"manifest":{…},"origin":…}`. The index is schema version 2, new with the origin in each entry: no app built a `FileDesignStore` before it, so no device has an older store and nothing migrates. The origin is read as strictly as the rest of the entry: an origin name the store knows (the file form of `DesignOrigin` is the store's own, so a new origin does not compile until it has a name); an unknown name makes the index corrupt. An origin added later bumps the index version.
- One write commits a design: every save holds the exclusive lock, writes the package file, then the index, atomically, and nothing after the index. The index carries the listing, the generation and the origin together, so a design is never listed without the origin its save gave it. A save that stops before or during the index write leaves the listing, the generations and every origin as they were, and can leave a package file the index does not list, which is not reported and which the next save drops. A first bundled install that fails therefore leaves nothing installed, and the next sync installs the design, even from a newer bundle.
- Nothing is written that could not be read back (R12): before the first write of a save or an adoption, the index is encoded, checked against its cap and read back through the same strict reader as a read, and a failure is `wouldNotReadBack`.
- A design whose entry has no `origin` (an index written by hand or by another tool) has no recorded origin. The store reads such an entry and never writes one. The sync adopts it when it is the bundled design (`adoptAsBundled`), which rewrites the index in one write with that entry's origin set to `bundled`, and otherwise it counts as an import, a conflict: a newer bundle never replaces it.

**`CVBundledDesigns`** holds the bundled `.mcvt` files as resources, served as raw bytes through `Bundle.module`. `professional`, `modern` and `minimal` are written against markup contract 1 and pinned by hash to their `id@version`, since the catalog's sync never replaces a design of the same version: a changed package needs a new version.

**`CVRendering`**
- **`DocumentHTMLBuilder`:**
  - produces the markup contract, with closed `Tag` and `Attr` enums and per-scalar escaping;
  - validates the language tag;
  - keeps only `WebLink`s, and prints each link's destination as its text;
  - formats dates in the document language.
- **`HeadingsCatalog`:** JSON heading tables per language plus an index, matched by BCP 47. An unsupported language is a typed error. It reads the tables as raw bytes through **`HeadingTableSource`**, its outbound port, and decodes them itself; only a tag that reads as BCP 47 reaches the source ([ADR 0026](adr/0026-keep-the-core-portable-to-android.md)).
- **`PDFRendering`**, the outbound port: `render(html:page:) async throws -> RenderedPDF`, with `data`, `pageCount` and `requiredPages`. `truncated` is derived from those.
- **`PDFInspecting`**, the outbound port that reads the page count and text of a PDF.
- **`PDFLayoutInspecting`** refines it with `layout(of:)`: each page's box, and each text line with its page, its box (points, origin at the lower left, as in PDF) and its glyph height.
- **`RenderedDocument`:** the builder's output, meaning the HTML plus the exact text nodes it contains.
- **`DocumentCompleteness`:** every text node needs its own span of the PDF text, which no other node uses, ignoring case and spacing.
  - The search has a budget of 100 000 steps, and `report(in:expected:)` says how many it used. A search that runs out of budget reads as incomplete.
  - On the real renderers (macOS 27 and the iOS 26.5 simulator) the contract fixture uses 41 steps, and the flex and grid designs 12 each; a test keeps them under a tenth of the budget.
- **`GeometricCompleteness`:** every text line lies inside its page, within 1 pt, and its glyphs are at least 6 pt high (`minimumGlyphHeight`; the CSS policy allows 7 pt and up). A line of unknown height, and a layout with no page or no text, fail.
- **`FixtureRenderingGate`:** implements the catalog's `DesignRenderingGate`. It renders a fixture that uses every section with the candidate design, in the design's own default palette (palettes change colours only), once under every `FontScheme`, the design's default first, because a user can choose any font scheme and fonts change pagination. Each PDF must be complete and untruncated, and its geometry must pass (`Rejection.outsidePage`, `Rejection.glyphTooSmall` otherwise); the first that does not fails the design.
- **`GateFixture`:** the gate's document, in Italian with every kind of section, which the bundled designs were proven against on both renderers. `FixtureRenderingGate` prints it, and the native renderers' contract runs print the same document (`ContractFixture.document` is it), so a change to it means running the gate again on both.
- **Policy:** the required fields and page limit, shared by preview and export.

**`CVBundledHeadings`** holds the heading tables as resources, served as raw bytes through `Bundle.module` by `BundleHeadingTableSource`. An Android app ships no SwiftPM bundle: its edge reads the same files from the app's assets and passes them through the same port ([ADR 0026](adr/0026-keep-the-core-portable-to-android.md)).

**`CVRenderingWebKitSupport`**
- `SecureWebViewConfiguration.compileRules()` is called once by the composition root: a block rule per network scheme, plus a block on every subresource type. `make(rules:)` then builds each configuration: JavaScript off for content, non-persistent store, media only on user action.
- `SingleLoadNavigationDelegate` loads the HTML string with no base URL, reports when that load has finished, and cancels every later navigation.
- `DocumentReadiness` waits until the document is complete and its fonts are ready. Its script runs in a content world of its own, with a timeout.
- Content blockers do not see `data:` URLs on Apple platforms: a test records this. None can enter the document, because the builder emits only http(s) links and the CSS policy has no `url()` (R8).
- A clicked link, which only happens in the preview, may open a connection to its host before the navigation is cancelled (a WebKit preconnect). Nothing is sent over it. A document's links and a refresh make no connection at all; tests record both.
- Every file is wrapped in `#if canImport(WebKit)`.
- **`CVRenderingWebKitSupportTests`** check each of these on iOS and macOS. Each network test has a control without the rules, which shows that the test can see a request.
- The control of the `file:` test cannot show a load on macOS 27: there WebKit itself blocks a `file:` image in a page loaded from a string under a `file:` base URL. The rules are proven against `file:` on the releases that load it (iOS 26 and 27, macOS 26); the test records which.
- On iOS the exporter's tests run through the shared `ExporterTests` scheme, which holds the new test targets only: the package scheme also builds the legacy targets, which do not build for iOS.

**`CVRenderingIOS`, `CVRenderingMacOS`**
- One `PDFRendering` implementation per platform ([ADR 0003](adr/0003-one-pdf-renderer-per-platform.md)). Every file is wrapped in its platform condition.
- On iOS the web view is never put in a window. A `UIPrintPageRenderer` with a fixed paper and printable area paginates it, and each page is drawn in turn into a `UIGraphicsPDFRenderer` context, with a check for cancellation before each one. No step waits on a print callback, so a stalled print cannot hang the export (#101); the load and the readiness wait have time limits.

**`CVRenderingPDFKitInspector`**
- `PDFLayoutInspecting` on PDFKit, used by the export workflow and by the native contract tests. Every file is wrapped in `#if canImport(PDFKit)`; it imports AppKit on macOS and UIKit on iOS, for the font type.
- A line is one of PDFKit's `selectionsByLine()` over the whole page, and its box is the selection's bounds in page space, whatever the page's rotation.
- A line's glyph height is the smallest `.font` point size of its attributed string, the page's transform included. A line with a character that has no font gets none, so the geometry check rejects it.
- Text drawn wholly outside the page is not in the page's text at all, so `DocumentCompleteness` reports it; text that crosses an edge is a line whose box crosses it.
- **`CVRenderingPDFKitInspectorTests`** check this on iOS and macOS against PDFs drawn with CoreText at known positions: boxes and sizes, text past each edge, 3 pt text and text shrunk by a transform, a rotated page, a line with no font, and data that is not a PDF.

**Test support and tests.**

  - the **`PDFRendering` contract suite**:
    - the fixture must fit and contain every field;

    - deterministic pre-start cancellation;
  - `FakePDFRenderer`, which writes real uncompressed PDFs;
  - `MinimalPDFInspector`.
- **`CVRenderingNativeTestSupport`** (iOS and macOS) holds what both native renderers' tests share: `NativeRendererChecks`, the loopback listener that counts connections, and `DrawnPDF`, which draws PDFs with CoreText. It may import `CVRendering`, `CVRenderingTestSupport`, `CVRenderingPDFKitInspector`, `CVDocumentModel`, `CVDesignCatalog`, `CVBundledHeadings`, CoreGraphics, CoreText, Foundation, Network, PDFKit, Synchronization and WebKit (the listener's control page).
- **`CVRenderingIOSTests` and `CVRenderingMacOSTests`** run the contract suite against the real renderers with the PDFKit inspector: `xcodebuild test` on the iOS simulator, `swift test` on macOS. They also run the long-document pagination test and in-flight cancellation. `BundledDesignsPreviewTests` prints an English sample with each bundled design, in the design's default palette and font scheme, and stores the first page as the design's preview when `UPDATE_PREVIEWS=1`; it imports `CVDocumentModel`, `CVDesignCatalog`, `CVBundledDesigns` and `CVBundledHeadings`. They run the checks of `NativeRendererChecks`, one line each:
  - a field the renderer drops is reported missing;
  - flex and grid at the minimum column gap keep skills, profiles and interests apart;
  - R8: a script does not run; a remote image, stylesheet and font, a link and a meta refresh make no connection; the PDF keeps the document's text;

**`PrestoCVWorkflowPorts`**
- The ports that view models consume: `CVEditing` (new, load, save, rename, duplicate, delete, and the writer of the open CV, which writes its text and changes its look or document language), `CVBrowsing` (the list with the store's issues, the first-run state, the samples) and `CVExporting`. The editing and browsing operations have typed `throws(EditFailure)`; `CVExporting` and `CVAutosaveWriting` have untyped `throws`, so cancellation passes through.
- `LookOptionsProviding` (step 5-6): the designs, palettes and font schemes a picker offers, as ids, name codes and what each is drawn with (`LookOptions`, `LookOption`, `LookSample`: a design's page picture, a palette's main colour over its background, the kind of typeface of a font scheme), each design's own palette and fonts (`ownLooks`, a `DesignOwnLook` each), and the default design, which with its own palette and fonts is the look it shows for a CV that keeps none. The port belongs to its consumer (R3); its adapter is `CatalogLookOptions` in `PrestoCVIntegration`, on the design catalog.
- `LicenceNoticesReading` (#504): the notices the Licences screen lists, in its order (`LicenceNotice`: an id, a title, whether it is about the work of others, its text, and the `Licence` it names, with that licence's name and whole text). The port belongs to its consumer (R3); its adapter is `LicenceNoticesFile` in `PrestoCVIntegration`.
- `DiagnosticsReading` (#405, ADR 0032): what the Diagnostics screen of a test build reads, in the screen's own terms: whether it is offered (`isAvailable()`, `false` for every build that may not record), the stored runs newest first (`DiagnosticRun`: an id, a `DiagnosticRunKind` (`aiDraft`, `textImport`), the start date, a `DiagnosticRunOutcome` (`finished`, `failed`, `cancelled`, `unfinished` for a run that never ended) and the plain-text summary as it is shared), the copies of a run's files to share (`shareCopies(of:)`, which throws when a copy cannot be made) and `discardCopies()`: each reader keeps one set of copies of its own, which each copy replaces. The port belongs to its consumer (R3); its adapter is the composition's `TraceDiagnostics`, over the trace, so that `PrestoCVPresentation` sees no trace type (R5).
- App value types: `ExportOutcome`, `ExportFailure`, `EditFailure` (conflict with the stored revision, deleted elsewhere, too large, not enough content, a text too long or a section with too many entries, the CV too large, unavailable).
- `CVImporting` (`importCV(fromText:)` and `importCV(fromPDF:)`, untyped `throws`) with its value types: `ImportOutcome` (an unsaved `CV`, its review items and the text not imported), `ImportReviewItem` (a field, a reason and the person's own text), `ImportReviewField` (entries counted from one), `ImportReviewReason` (codes, no words: R13) and `ImportFailure` (with `fileNotRead`, for a file that could not be read). A PDF goes to the import as a PDF, never as a text taken out of it first (ADR 0027). The port knows nothing of the import's own types: the consumer owns it (R3).
- `ImportFileReading` (step 5-7b): `receive(_:)` is called once for each URL handed to the import screen, before anything else, and gives a `ReceivedFile` (an id and the URL); the adapter captures there whatever identity of the file it needs. `readPDF(of:)` reads a received file within the size bound, and `release(_:)` is called exactly once for each received file, after the import that reads it has ended (however it ended) or at once when the screen does not read it. Two received files may be the same file: the adapter counts them and lets the file go when the last one of that file is released, as each start of security-scoped access has its own stop. Its adapter is `ImportFileAdapter`, in `PrestoCVImportFiles` (step 5-8d).
- `CVLanguageDetecting` (#407): the language a CV's own words are written in, among the languages its PDF can be written in, or nil when they tell none; the export sheet asks it for a CV that keeps no language. `PrestoCVIntegration` makes `DetectDocumentLanguage` of the application layer conform to it, and the composition gives that the system's reader (`NaturalLanguageTextReader`).
- `LegacyLeftoversCleaning` (step 5-17e): `clean()` removes what the released app left under Application Support and holds nothing the person wrote. It is `async` and never throws: a removal that fails is logged, and the next launch tries again. Its adapter is `LegacyLeftoversAdapter`, in `PrestoCVLegacyLeftovers`.
- `ExportFileSharing` (step 5-12b): `write(_:named:)` writes an export's PDF as a file for the system's share sheet and gives a `SharedFile` (an id and the URL); `remove(_:)` is called exactly once for each written file, when the share that reads it has ended or at once when no share will read it. Its adapter is `ExportFileAdapter`, in `PrestoCVExportFiles`.
- `LegacyImportReviewing` and `LegacyReportReminding` (#406), the ports of the import report: the summary of the launch's import (`LegacyImportSummary`: the details each stored CV lost, and those it keeps to check, by `CVID`; the CVs left out, by `LegacyLeftOut`; whether the import did not run) and the removal of the old copies of the CVs the report showed (`removeOldCopies(of:)`; the others keep theirs), which gives the CVs whose old copy stays; whether the report shows again, and the person's choice not to be reminded, which throws `LegacyReminderFailure.notKept` when it cannot be kept. Their adapters are `LegacyImportReview` in `PrestoCVIntegration` and `LegacyReportMarker` in `PrestoCVComposition`.

**`PrestoCVIntegration`**
- **Workflows**, implementing the ports:
  - `EditCVWorkflow` and `BrowseCVsWorkflow`, on the use cases of the application layer, with `EditFailureMapping` (every `AuthoringError` has its `EditFailure`, an exhaustive switch). A duplicate keeps design and language; the title of a copy is composed by the view model. `BrowseCVsWorkflow` keeps, for the launch, every file the store reported it could not read, one issue per file, and gives them all with each listing: the store reports a file once, on the listing that sets it aside, which at launch is the first-run screen's. The autosave writer keeps the CV the store returned last and writes the editor's content onto it (`CV.holding(contentOf:)`, text only), so a revision is never taken from the editor; a write of the open CV goes through the writer, one at a time (the look and the language too), and takes only the editor's text; a write that reached the store is done even if its task was cancelled, one that did not throws `CancellationError`;
  - `ExportCVWorkflow`: from the editor snapshot, with the document language, through the renderer, then the completeness check on the actual PDF. In order: the CV is ready (`notReady`), the headings of the language (`unsupportedLanguage`, never a fallback; a table that cannot be read is `renderingFailed`), the mapped document is valid (`invalidDocument`), the render on the page of the `ExportPolicy`, the text completeness check (`incomplete`, with the number of texts missing), then the geometric check on the layout of the PDF (`textNotVisible`, with the number of lines outside their page or under `GeometricCompleteness.minimumGlyphHeight`; a layout that cannot be read is `renderingFailed`). The workflow takes a `PDFLayoutInspecting`. A PDF shorter than the CV needs is an outcome, not a failure: `ExportOutcome.truncated`, with both page counts; its text is cut, so neither check applies to it. The look (stylesheet, palette, fonts) is a `DocumentStyle` it is given;
  - `DesignResolvingExporter`, the `CVExporting` the composition root wires: it resolves the CV's design choice through the catalog's `ResolveDesign` into a `DocumentStyle`, then exports through `ExportCVWorkflow`. A CV that keeps no design, and a design the catalog does not have, export with the default design, and the CV keeps its palette and fonts (as in version 1); a palette or fonts the CV does not name, or the catalog does not know, are the design's own. A store that fails, or that lacks the default design, is `renderingFailed`, with nothing rendered; a cancelled task stays a `CancellationError`;
  - `CatalogLookOptions`, the `LookOptionsProviding` adapter: the installed designs in the catalog's order, every `NamedPalette` and `FontScheme`, the default design, and the own palette and fonts of each installed design and of the default design, installed or not; each option is named by a code (`design.<id>`, `palette.<id>`, `fonts.<id>`) the view words (R13), and carries its sample: the design's preview picture, the palette's primary and background colours, the font scheme's typeface;
  - `LicenceNoticesFile`, the `LicenceNoticesReading` adapter: it decodes the notices file the app bundles (`Resources/Licences.json`: each licence's text once, under `licences`, and the `notices`, each naming its licence by id) from the bytes the composition reads for it each time the screen asks; bytes that are not that file are `unreadable`, a notice naming a licence the file lacks is `unknownLicence` with its id, and an error of the read, a cancellation included, passes through;
  - `BrowseDesigns`;
  - `DraftCVWithAI`: availability, then draft, then an unsaved CV plus its gaps;
  - `LegacyImportReview` (#406): the `LegacyImportReviewing` of the launch, read from its `LegacyImportOutcome`; it gives the report's drops and checks apart, and removes the old copies of the CVs it is given, and only theirs, through the same `ImportLegacyStore` (`acknowledgeLosses(of:)`), and gives the CVs whose old copy stays. `BrowseCVsWorkflow` takes the outcome too: while it may leave CVs out, `onboarding()` is `returning`, so a store that is empty because the import failed is never the welcome of a new app;
  - `ImportCVWorkflow` ([ADR 0027](adr/0027-import-a-cv-from-its-text-with-rules.md)): the text or the PDF goes through the import (a `CVTextImporting`, `ImportCV` in the app; a PDF through its PDF entry, with the layout of its words), then `ImportedCVMapper` makes an unsaved CV plus its review list and the text not imported. The CV has an id from the `IDGenerator`, revision 0 and nothing stored, and a CV the save rules would refuse for its size is returned all the same. Every `ImportError` is an `ImportFailure` of its own (an error that is neither, `unreadable`); a cancelled task stays a `CancellationError`.
- **Mappers:** `CVToDocumentMapper` (`CV → CVDocument`), `CVDraft → CV` and, when the import is wired in, `ImportedCV → CV` (`ImportedCVMapper`). They are exhaustive and deterministic, with typed dates. The draft mapper uses `Period.make` and reports every gap.
  - `ImportedCVMapper` writes only values of the import, plus the bullets that join an entry's lines when there are several. What the CV cannot hold is reported with the person's own text, and the text goes to the text not imported, never dropped: a language without a CEFR level (`levelMissing`, `levelNotCEFR`, `levelsDiffer`), an education's place (the CV's education has none: `locationNotKept`), a certification year outside 1900–2200, another website after the first, and a period that is not a range `Period.make` accepts (a single date: `periodNotARange`; an end before the start: `periodUnreadable`). A period without an end keeps an unknown end, never "present"; only a stated present is current. The CV's document language is the detected one or none. The text of the person is not cleaned: the control and bidirectional characters are left to the rules of the domain (#102). `ReviewItemMapping` maps the core's reasons and fields with no `default:`, and counts entries from one. `ImportMirrorCompletenessTests` walks a fully populated `ImportedCV` (`Mirror`, and the list `ImportedCV.fields`): every leaf must be in the table of leaves mapped or in the table of leaves reported, and a leaf in neither fails.
  - `CVToDocumentMapper` trims text and prints no blank value. An item with nothing to print is left out: a skill, a language or a certification whose name is blank, an experience or education entry whose fields are all blank (a profile always has its address); an entry with some value prints what it has. The text it prints is what the exporter's validator accepts, for any text the domain can hold today: CRLF and CR become LF in the multi-line fields (summary, descriptions), a tab becomes a space, a line break in a single-line field becomes a space, any other control character and the bidirectional overrides are dropped (the rule of the domain itself is #102). A link the domain accepts is printed: the exporter's rule is the looser one for http and https, a test pins that they agree, and the workflow fails with `invalidDocument` on any link the exporter would drop or rewrite, never silently. Sections come in print order (summary, experience, education, skills, languages, certifications, profiles, interests) and an empty one is left out. Left out on purpose: the CV's list title, the identity and bookkeeping fields, the design choice (the export resolves it), and the month of a certification (the document prints a year). `MirrorCompletenessTests` walks a fully populated CV with `Mirror`, down to enums, booleans and optionals. Every leaf of the CV must be at its own place in the document, written as the test's table says (the same, trimmed or renamed), or be in the table of leaves left out, with a reason; a leaf in neither fails. Every leaf of the document must come from a leaf of the CV or be the document's own, and the fixture holds no value twice, so a value can only come from its own field.
- **`PrestoCVIntegrationTests`** may import `PrestoCVIntegration`, `PrestoCVWorkflowPorts`, `PrestoCVApplication`, `PrestoCVCoreTestSupport` (the in-memory repository, the clock and the fixtures), `PrestoCVDomain`, `PrestoCVImporting`, `PrestoCVImportingTestSupport`, `CVDocumentModel`, `CVDesignCatalog`, `CVRendering`, `CVRenderingTestSupport` (the fake renderer and the PDF inspector for Linux), `CVBundledHeadings`, Testing, Foundation. They run on Linux with `swift test --package-path PrestoCVApp`.

**`PrestoCVPresentation`**
- `@Observable @MainActor` view models whose public API holds presentation types only: status enums, and no domain types.
- **Saves** are serialised and coalesced, and every caller waits for its own edits to land.
- **Save and export** each have their own status, in their own view model (the editor, the export sheet), reset when a new intent starts.
- **A status that keeps the person in the CV** (`SaveStatus.blocksLeaving`: `conflict`, `deletedElsewhere`, `failed`, `tooLarge`, `textTooLong`, `tooManyEntries`) offers its ways on as `StatusAction` codes (`statusActions`), in the order the notice shows them: a **conflict** offers reload or save as a copy; **deleted elsewhere** offers save as a copy or discard; a **failed** write offers to try again; a text or a CV above its limit offers none, as the person shortens the text.
- **`EditorChrome`** is the rule of the room the editor's notice takes (#402, decision 9): where the form is short of room (`isCompactHeight` or `isAccessibilitySize`, so `isShortOfRoom`), `noticeHeight(fullHeight:editorHeight:)` caps the notice at `noticeShareOfHeight` (a quarter) of the editor's height, and the notice scrolls inside; elsewhere, or while the editor's height is not known, it is nil and the notice takes its own height.
- **View-model initialisers do no I/O.** Loading happens in the view's `.task`, so the factory can be called on every view init.
- **`EditorViewModel`** (step 5-5) opens an `EditorStart` (a stored `CVReference`, a blank CV, or a `CVDraft` not stored yet; `OpeningStatus`), holds the form as `EditorContent` (the title, the personal details and the seven sections as lists of rows: `ExperienceRow`, `EducationRow`, `SkillRow`, `LanguageRow`, `CertificationRow`, `ProfileRow` and `InterestRow`, each row with a `RowID` the editor made: opaque, unique in the editor's life, never in the CV; a view lists the rows by their ids (each row is `Identifiable`) and binds a row's fields through `rows[row:or:]`, which finds the row by its id wherever it stands, reads a row that went as the row last shown, and drops a write to it (#32); a date is its `DateParts` (the year as typed, empty by default and never "0", and a month or none) and a period its `PeriodParts` (a start, an end, and whether it goes on: turning that on clears the end, and `asksForEnd` says whether the form asks for one); the domain reads the parts with `PartialDate(reading:)` and `Period.reading` and writes them back, a period or a date it cannot read is `unreadable` with its field, a period that ends before it starts is `endBeforeStart`, and neither is stored). `addRow(to:)`, `removeRow(in:id:)`, `confirmRemoval()` and `cancelRemoval()` edit the rows: `addRow` puts a new job, study or certification first, as a CV lists the newest first, and any other row last; a row with nothing in it goes at once, any other waits in `pendingRemoval` (a `RowRemoval`, which names the row by its id: it removes that row if it is still in its section, and nothing otherwise; `load()` and `reload()` clear it; it carries the row's `RowName`, the first text among the fields that say what the row is, or a placeholder of its section, which the view words); `addedRow` is the row just added, which the view focuses and scrolls into view, then reports with `rowWasShown()`; `moveRow(in:id:by:)` moves a row up or down by places, `canMoveRow(in:id:by:)` says whether it can, and `moveRows(in:from:to:)` takes a move as a list's drag reports it (the places of the rows and the place before which they go), a move that changes no place or names one outside the section doing nothing (`RowOrder`), and `canReorderRows(in:)` says whether a section has two rows or more, `reordersRows` whether some section has; where the view reports a narrow screen (`layoutChanged(isNarrow:)`), a job, study, language, certification or profile shows in the form as a line, its `summary` (an `EntrySummary`: the texts that name it, its `EntryYears`, the other texts of the line and a language's level as a code, which the view words), and opens on a page of its own (`showsOnAPage(_:)`): `openedEntry` is the `EditorEntry` (its section and its id) the page shows, `openEntry(in:id:)` opens it and `closeEntry()` closes it, a row added there opens its page, and the page closes when its row goes or the screen widens; `showsMoveHint(in:)` says whether the section tells how to move a row (two or more on lines), and `asksToRemove(row:onItsPage:)` whether a removal waits for the answer on the page or in the form, so that one question shows; a skill and an interest stay in the form; `EditorChoices` gives the choices of the editor's menus as codes the view words (the skill levels and the language proficiencies the domain can store, and the months of a date); the order of a date's month and year is the app's (`MonthOrder`), not the presentation's; each add, move or remove is an edit for the autosave, and gives each change to the `Autosave` of the application layer through the port's autosave writer. `SaveStatus` comes from the autosave's status, the last write's `EditFailure` and the domain's `saveCheck()`, with `EditorField` and `EditorSection` naming what is wrong; text that cannot be read as an address is `unreadable` and the rest is stored. `reload()` and `saveAsCopy()` replace the CV the form stands on, each with a new autosave and writer; edits made meanwhile are written after. `exportSnapshot()` gives the form as it stands, stored or not, as an `ExportSnapshot` for the export sheet; it reads no store and leaves `SaveStatus` alone. `setDocumentLanguage(_:)` (a tag, nil for automatic) and `changeLook(to:parts:)` (an `EditorLook` and the `LookPart`s chosen) go to the writer of the open CV, which stores them, or keeps them for the first write; the editor holds the CV the writer gives back for what it shows, gives to the export sheet and copies, and no write carries its look or language. Each `EditorField` names the kind of text it asks for as a `FieldInput` code, which the view turns into a keyboard (R13). `FieldEntry` says what a field keeps of a change the person made: a field of one line takes no line break, even where it wraps at a large text size, so its return key moves the focus to the next field of the details (`EditorField.nextDetail`, nil in a section, which ends the editing) and leaves the text as it was, and a break that comes with other text, such as a pasted one, becomes a space; a paragraph keeps its breaks. A text field can hand the same text over twice, and `FieldEntries` makes that one entry: the same text handed over again, while the field holds what it kept of it, changes nothing, where `FieldEntry` alone would read a pasted break, kept as a space, as the return key over that space. A field that cannot be stored is a `FieldProblem` (its row, its field and a code) only once the person has left it (`fieldWasLeft(_:row:)`) or tried to store (`saveNow()`), never while they type, and it goes as soon as it no longer holds (`problems`, in the form's order; `problem(of:row:)` gives the code of the one a field of the details or of a row shows a note for); the list's `saveWhatItShows()` is no attempt of the person and names none. `announcement` is what VoiceOver is still to tell of the changes, as one `EditorAnnouncement` (where the status settled, then the problems met that the status does not name, in the form's order), so that no announcement cuts another short: nil until the status settles somewhere other than where it stood when the CV opened, or a problem is met; `pending` and `saving` settle nowhere, so a save that went well tells nothing, and a problem, a failure, and the save after one or the first save of a new CV each do. A change made before the view told the one before joins it; the view reports what it told with `announcementWasTold(_:)`, and a report of an older one keeps what came after it. The editor calls the `storeChanged` closure it is made with when the store changed: after each write the store took, and once each time a write, a reload or a copy finds that another save or a deletion changed the CV (the list in this window then shows the CVs as stored); never for a write refused otherwise.
- **`CVListViewModel`** (step 5-6) lists the CVs as `CVRow`s (a `CVReference`, the `label` the row shows, the subtitle, the last-saved instant and the language tag) in the order of `CVBrowsing.list()`. The label comes from `CVTitle.labels`, which the list gives the view's words for an untitled CV and for numbering a title (`untitled` and `numbered`, as the editor gets `copyTitle`), so no two rows read alike (R6, R13). The store's issues are a `StoreNotice` of kinds and a count, never a path, that the person can dismiss for the launch; one issue hides no CV. `rename`, `duplicate(title:)`, `delete` and `setDocumentLanguage` act on the CV the list read for the row, at its revision, and read the store again; a conflict or a CV gone is a `RowStatus` and the list reloads; a list that cannot be read after a change keeps its rows and is `isStale`. The list waits for the `editorsStored` closure before it reads the store, and `now` moves only when the list is read or `refreshNow()` is called. A cancelled task sets no failure. What the column shows is decided there too (step 5-10b, R5): `content` (loading, empty or rows), the `notices` in order (stale, failed, the unreadable files), the `rowActions` of the menu and of VoiceOver and the subset a swipe offers, and the row failures, one `ListNotice.rowFailure(RowFailure)` each (the `CVReference`, the label, the `RowStatus` and the failure's number): every failure still pending shows at once in `notices`, after the store's own, listed rows first in list order by their current label, then the rows no longer listed (another action or a reload removed them) in the order the failures were found, named by the label the row had when the change began. A row is told once, by its latest failure. `dismissRowFailure(_:)` removes the status and the entry of that failure only when it is still the row's latest, so a newer failure of the same row stays; a change of the row that worked removes its notice, and a reload keeps the notices of the rows with an entry. A row carries the stored `title` beside its label, which the rename starts from. `keptNotices(_:)` places the notices of the shell's kept editors (`KeptEditor`, #402, decisions 16 and 17) as `KeptNotices`: each `KeptNotice` has the kept editor's id, a label, its `SaveStatus` and whether it offers to write again (`canRetry`: only after a write that failed or did not end); the one of a listed CV goes `under` its row and is named by the row's label, any other goes `above` the rows, named by the title its editor's text gives it, and with two kept editors of one listed CV the last one left goes under the row and the earlier ones above, in the order they were left.
- **`FirstRunViewModel`** reads `onboarding()` (first run only when the store holds no CV and no issue) and, once, `samples()`. `entries` are what the start screen shows, in order, and the screen decides nothing about them: the import, then the examples as one `StartEntry.examples` (each an `ExampleChoice` with its title and the `summary` that tells two examples apart), then blank; `StartChoice` is only what the person chose, the argument of `start(_:)`. The import is offered only when the initialiser's `offersImport` says so; the composition passes true, and the shell shows the import (step 5-13). Blank and an example give a `CVDraft` under a new identity and store nothing, the import is a `StartDestination` the screen turns into the import flow. When the examples cannot be read, an `examplesIssue` entry stands where theirs would be, then blank (and the import first, if offered); a later successful read replaces it by the examples.
- **`LegacyImportReportViewModel`** (#406, step 5-17a) reads the summary once (`load()`): two groups of `LegacyReportRow`s, the CVs that lost details (`leftOut`) and those that keep some as written to check (`toCheck`), each in the list's order and by the list's label (`CVListViewModel.labels`), with each `LegacyDetail` once in a set order; the CVs not imported as `NotImportedCount`s by `NotImportedCause`; and a `LegacyImportNotice` for the list (how many were not imported, or that the import did not run, never a count it does not know). The sheet shows (`LegacyReportState.review`) only when a group has a row and the reminder says so; the list's mark comes from the summary, not from the rows: `isIncomplete(_:)` is true for a CV that lost details while its old copy stays, also when the sheet does not show or the list could not be read. `confirm()` removes, once, the old copies of the CVs the sheet shows and no other (`removing`, which cannot be closed), then `removed`, or `keptSome` with how many stay until the person closes it; the CVs whose old copy stays, shown or not, keep the mark. `close()` from the review keeps the old copies and, with `remindsNoMore` checked, stores the choice in the background; a choice that cannot be stored unchecks itself.
- **`ShellNavigationModel`** holds what the detail shows (an `EditorStart`: a stored CV, or a draft not stored yet), its `editor`, made by the closure the shell is given, the selected row and the column a compact screen shows first. `screen(for:)` gives what the window shows from the first run's state: loading, the welcome while a first run has nothing open, otherwise the split view. `open(_:)` and `deselect()` give a `LeaveVerdict`: `left`, at once, without waiting for the store, or `stayed` with the `SaveStatus` that keeps the person in the CV, while its text is one no write can store as it is (`conflict`, `deletedElsewhere`, `failed`, `tooLarge`, `textTooLong`, `tooManyEntries`), so that it is never lost; `canLeave` is false meanwhile, so that the view offers no way back. An editor left is stored after it is closed (`saveNow()`), and the shell keeps it until that ended; opening that CV again meanwhile gets the same editor back, found by the CV it stores now (a draft stores one from its first write on), so that one writer keeps its writes in order. When the scene stops being active (`sceneChanged(isActive:)`), the shell stores the open editor and waits for those left, under a `BackgroundHold` asked of the `BackgroundTime` it is given, which the app's platform layer implements (a background task of `UIApplication` on iOS, nothing on macOS) and gives back once every write ended. A stored CV closes when its row goes, unless its text is not stored; a draft stays, as it has no row. An editor left whose write did not store its text (it failed, or a field cannot be read) is kept, so that nothing typed is dropped (#402, decisions 16 and 17); one whose status is `saved` or `notEnoughContent` is not. `keptEditors` lists them in the order they were left, for the list's notices; `retryKept(_:)` writes one again and `openKept(_:)` opens it in place of what was open, as `open(_:)` does; storing every editor on the way out writes the kept ones too, and one stored since is no longer kept. `discardEditor()` drops the open editor and its text not stored, on the person's word (after a deletion elsewhere, or when a CV cannot be opened); nothing is written. `showImport()` puts the import (`importer`, made by the closure the shell is given) in the detail in place of what was open, with the same `LeaveVerdict`, and it counts as open for `screen(for:)` and the column a compact screen shows; a change of the list leaves it. Opening a CV or a draft, `deselect()` and a collapsed split view's sidebar stop a running import and drop it, with its text (#404, decision 9). The view forwards each change of the import's status (`importStatusChanged()`) and decides nothing: a ready import's draft opens in the editor like any draft, and the import goes; the editor stores the draft when the person leaves it, edited or not (decision 6).
- **`LookViewModel`** shows the `LookChoices` it is given and the look the CV holds (the defaults for a CV that keeps none). Each `LookChoice` carries what the view draws it with (`LookChoice.Sample`: a page picture, a palette's main colour over its background, a typeface), mapped from the port's `LookSample` into this module's own values, because a view imports `PrestoCVPresentation` alone. `choose(design:)`, `choose(palette:)` and `choose(fonts:)` mark a part as chosen; `apply()` sends the choices as one `LookChange` (`LookChange.followed(by:)`) through the writer of the CV, so an id the app does not know stays unless chosen, a CV saved elsewhere is `LookStatus.conflict` and the text is never written.
- **`ExportSheetViewModel`** (step 5-7a) exports the `ExportSnapshot` it is given through the `CVExporting` port, in the language chosen in the sheet (an `ExportLanguage`; nil is automatic: the CV's language, else the language its words are written in, else the app's), and takes a choice to the CV through a callback. `start()`, `select(language:)` and `refresh()` cancel the running export and start a new one after a pause on the injected clock, so that quick changes make one export; `stop()` cancels and clears. A task publishes only while it holds the latest intent, so a late result changes nothing. The snapshot is read once, after the pause: a blocker of `ExportMissing` is `notReady` and starts no export; the warnings are shown only. For a CV that keeps no language, the sheet reads its words through `CVLanguageDetecting` (`automaticLanguage` shows the result) until they tell a language, and then no more; the first one found goes to the CV through a second callback (`onLanguageFound`), unless a language was chosen in the sheet, which goes to the CV instead. While the words tell none, the PDF is in the app's language and nothing goes to the CV, so a later export reads them again; choosing automatic forgets what was found, as the CV forgets its own (#407). The sheet shows the look of its PDF (`shownLook`, an `EditorLook`: the CV's, else the default design with its own palette and fonts) among the `lookChoices` (#407): `choose(design:)`, `choose(palette:)` and `choose(fonts:)` show the part at once, export it after the pause and take the whole look and the part chosen to the CV through a third callback (`onLookChosen`). Only the parts chosen in the sheet replace the CV's in the later exports; the others follow the CV each export reads, an id the app does not offer included. A choice of the look on screen keeps the PDF and its share, a choice of the look being made lets that export go on, and a look no design may have changes nothing. `lookPicker` (a `LookPickerModel`) gives the view the groups of the picker, design, fonts and palette in this order: the fonts and the palette start with the design's own, drawn with the palette and fonts of the design the PDF is made with, and an id the app no longer offers is one more item, last and chosen, with no name of its own; `pick(_:)` chooses the part of an item, nil for the design's own, and leaves the kept item alone. `ExportStatus` mirrors `ExportFailure` (`incomplete(missing:)` counts the texts the PDF lacks, `textNotVisible(lines:)` the lines outside their page or too small), and a cancellation is `idle`. It gives the `ExportedDocument` and its `suggestedFileName` (`PDFFileName`, with the pattern of the PDF's language, R13). `preview` (an `ExportPreview`) is what the sheet shows above its lines: the PDF on screen with its `ExportID`; while a new PDF is made after a PDF was on screen (a look or a language chosen, a new try), the PDF it replaces, which is never shared and never opens on the whole screen, two choices in a row keeping the first; and none before the first PDF, after a failure, for a CV not ready and after `stop()`. `share()` writes the PDF on screen through the `ExportFileSharing` port and opens a `PDFShare` (`openShare`), which the platform's share sheet reads; its `end(_:)` removes the file and, only for the PDF on screen, confirms a save to Files or a send by mail, message or AirDrop (`ShareOutcome`, read from `ShareResult(activity:completed:failed:)`; any other activity that went through, such as print or copy, confirms nothing) and marks a share that failed (`shareFailure`, a new `ShareFailure` each time; a file that cannot be written is one too). A new try, a share that goes through, a new export and `stop()` clear it. `shareAvailability` (`ShareAvailability`) is `preparing` while an export runs or the file is written, `unavailable` while there is no PDF to share, and `ready` otherwise; `closesAsDone` is true once a share went through. A second tap while a file is written or a share is open writes nothing; a new export and `stop()` let the share go, and a share that goes without an end still removes its file. `showFullPDF()` gives a `FullPDF` (the PDF on screen, its `ExportID` and its file name, the title of the screen) for the whole screen (step 5-12c); `closeFullPDF()` ends it, and so do a new export and `stop()`, so the whole screen never shows a PDF the sheet no longer holds.
- **`ImportViewModel`** (step 5-7b) imports a text typed or pasted (`paste(_:)` joins the strings by a new line; `canImportText` needs a letter), a PDF pasted (`importPDF(_:)`) or a file (`importFile(at:)`, read through `ImportFileReading`) through the `CVImporting` port, one import at a time. `ImportStatus` is `idle`, `importing`, `failed` with an `ImportProblem` (one for each `ImportFailure`; an error of the file port that is no import failure is `fileNotRead`, any other error of the import `unreadable`) or `ready`, and a cancellation is `idle`. The result is an `ImportedDraft`: an `EditorStart.draft` that nothing stored, its `ImportReview` (`ReviewEntry`s with a `ReviewedField` and a `ReviewReason`, mirrors of the port's, in its order and counting from one, the person's text as written, the text not imported whole, and the `ImportSource`) and, for a CV the store would refuse, its `SaveStatus`. A task publishes only while it holds the latest intent; `cancel()` drops a late result and `opened()` clears the draft once the editor has it. The screen calls `receive` for each file handed over, first. While an import runs, the file is not read and is released at once; otherwise the import task reads it and releases it when the task ends, after the result is published, however the import ended, also when the screen is gone. The task holds the port, not the screen. The view model never decides which files are the same and never asks the file system.
- **`ImportReviewViewModel`** shows an `ImportReview` beside the editor while it has entries or a text not imported, until `dismiss()` or `editorStored()` (the review ends when the person saves, ADR 0027).
- **`SettingsViewModel`** (#405) gives the Settings sheet its groups in order (support, legal, open source, about, and Diagnostics last) and the rows of each as codes (`SettingsGroup`, `SettingsRow`, R13), from values the composition passes (the support address, the privacy policy and source code links, the version, the build and the app's name). The support row is a `mailto:` link to the address with no subject and no body, built with `URLComponents`; an address that makes no link leaves the row out and the address still shows. The Diagnostics group (`SettingsGroup.Kind.diagnostics`, one `SettingsRow.diagnostics`) is there only while the trace of a test build records: `appear()` asks the `DiagnosticsReading` port once when the sheet appears (a later call, also while the first answer is pending, asks nothing), and the row fails closed, so it is absent until the answer comes and for every answer but an open gate.
- **`DiagnosticsViewModel`** (#405, ADR 0032) shows the Diagnostics screen of a test build, over `DiagnosticsReading`: `load()` reads the stored runs, lists them newest first (`DiagnosticsRow`: an id, a kind code, the start date and an outcome code, R13) and chooses the newest; `select(_:)` shows the chosen run's summary at once and makes the copies of its files to share (`shareFiles`), one choice at a time, since the reader keeps one set of copies and each copy replaces it: only the latest choice sets them, and a choice that a newer one replaced before its turn makes no copy; `finish()`, when the screen closes, discards the copies after every copy begun before it, so a copy that ends after the screen closed is never offered, and runs read after the screen closed are not listed. `DiagnosticsState` is `loading`, `empty` or `listed`. A copy that cannot be made leaves the summary and no files, and `copiesFailed` tells the view why there is nothing to share (a newer choice or a closed screen clears or never sets it). It exposes no trace type.
- **`LicencesViewModel`** (#504) reads the notices through `LicenceNoticesReading` when `load()` is called, never at init: `state` is `loading`, `loaded` or `failed` (a new `load()` tries again; a cancelled read changes nothing more), `rows` are the notices with the names of their licences, `othersState` is `noOthers` once the notices are read and none is about the work of others, and `detail(of:)` gives a notice's text and its licence's text in paragraphs (the lines between blank lines).
- **`PrestoCVPresentationTests`** may import `PrestoCVPresentation`, `PrestoCVWorkflowPorts`, `PrestoCVApplication`, `PrestoCVCoreTestSupport` (the in-memory repository, the manual clock and the id generator), `PrestoCVDomain`, Testing, Foundation, Synchronization, Observation (to see which writes a view model's properties reach the views). **`PrestoCVImportFiles`** (step 5-8d)
- `ImportFileAdapter` implements `ImportFileReading` over the `ImportFileSystem` seam; `SystemImportFiles` is the real file system, with POSIX calls, so the target is an outbound adapter and platform conditions are allowed in it (R11). The composition builds it with the system's copy folders and the size bound.
- **A file is known by its identity** (`FileIdentity`: the device and the file number), read with `lstat` on the resolved path when the file is received; only a regular file has one. A file without one is never read nor deleted: reading it is `fileNotRead`.
- **The read goes through one descriptor**, opened without following a link and without blocking, and only if `fstat` shows the same regular file. A size above the bound is `tooLarge` at once, and the read stops at the bound plus one byte, so a file that grows or reports a wrong size cannot make it unbounded. A cancelled task stays a `CancellationError`.
- **Receive and release share one lock:** receive counts the file under it, and release decides and deletes under it, so a copy received while the last one is released is counted first. Only a file directly in a copy folder (`tmp/<bundle>-Inbox` and `Documents/Inbox`), not in a folder under it, is deleted, never a file the person picked elsewhere: it is renamed aside to a hidden unique name in its folder, its identity is checked there, and it is unlinked only if it is the received file; otherwise it is put back.
- **The security scope** (under `#if canImport(Darwin)`; elsewhere a file has none) is opened at receive, before the identity is read, and closed once for each receive, outside the lock.
- **`PrestoCVImportFilesTests`** may import `PrestoCVImportFiles`, `PrestoCVWorkflowPorts`, `PrestoCVImporting`, `DiagnosticLogging`, `DiagnosticLoggingTestSupport`, Testing, Foundation, Synchronization, Glibc, Darwin and Android. They run on Linux with `swift test --package-path PrestoCVApp`, against the real file system in a temporary folder.

**`PrestoCVExportFiles`** (step 5-12b)
- `ExportFileAdapter` implements `ExportFileSharing` with Foundation's file calls. Each share's file is written atomically in a folder of its own, `<root>/<UUID>/<file name>`, so the share sheet never reads half a file and two shares of one PDF never read or remove each other's file. On iOS the file is written with complete protection unless open, so no one can open it once the device locks, while a service of the share sheet that has it open already can finish reading it; a Mac writes it with none, as the trace store does. `remove(_:)` deletes that folder; a second remove, or the remove of a file it never wrote, does nothing.
- **Making the adapter removes whatever is under its root**: the folders of shares an earlier launch could not remove or did not live to remove. The composition makes it once, at launch, before any write can start, so nothing of this launch is there yet.
- The root lies in the system's temporary folder, which no backup reads. A name is one file name (not empty, not `.` or `..`, without a slash or a null character, at most 255 UTF-8 bytes) or the write is `notAName`.
- The log names a kind of failure only, never the file's name (it holds the person's name) nor its path ([logging](../logging.md)).
- **`PrestoCVExportFilesTests`** may import `PrestoCVExportFiles`, `PrestoCVWorkflowPorts`, `DiagnosticLogging`, `DiagnosticLoggingTestSupport`, Testing, Foundation, Glibc, Darwin and Android. They run on Linux with `swift test --package-path PrestoCVApp`, against the real file system in a temporary folder.

**`PrestoCVLegacyLeftovers`** (step 5-17e)
- `LegacyLeftoversAdapter` implements `LegacyLeftoversCleaning` with Foundation's file calls, off the main actor (`@concurrent`, R19). It removes exactly three paths, all derived from Application Support by `LegacyLeftoverPaths`: the design files `PrestoCV/Templates` (a folder), their cache `TemplateCache` (a folder directly under it) and the export settings `PrestoCV/export-preferences.json` (a file). It never names, lists or walks anything else: `PrestoCV/CVs` and its `Quarantine`, `PrestoCV/UnsavedEdits`, `PrestoCV/StoredUnsavedEdits`, the new app's root, Diagnostics and the temporary folder are never touched.
- A path that is a link is removed as the link, never its target. A path that is not there counts as removed, so there is no mark of its own: the composition runs it at every launch whose import left nothing out, and the next ones find nothing. A removal that fails is logged by its kind (`templates`, `templateCache`, `exportPreferences`) and a code, never a path ([logging](../logging.md)); the others still go.
- **`PrestoCVLegacyLeftoversTests`** may import `PrestoCVLegacyLeftovers`, `PrestoCVWorkflowPorts`, `DiagnosticLogging`, `DiagnosticLoggingTestSupport`, Testing, Foundation, Glibc, Darwin and Android. They run on Linux with `swift test --package-path PrestoCVApp`, against the real file system in a temporary folder.

**`PrestoCVComposition`**
- The only place that creates infrastructure (R4). The `@main` App type holds it in a `static let`. It owns:

The paths come from `AppPaths.legacyLeftoversOnDevice()`, which uses the Application Support the legacy store lies in; a UI test's fixture folder gives paths of its own under `LegacySupport/`, so a launch with a fixture never removes the files of a device;

  - the `ScreenFactory` (`Composition.screens`): it makes the list, first-run (offering the import) and editor view models over the one repository, the clock and the ids, with the two workflows made once and shared, and the words (`untitled`, `numbered`, `copyTitle`) coming in from the caller (R13). ## Tools

Packages under `Tools/` that check the repository. They are `tool` targets in `rules.json`, so the checker applies only their import allow-lists, and nothing in the app depends on them.

- **`Tools/ArchitectureCheck`**: the architecture checker ([ADR 0006](adr/0006-enforce-architecture-mechanically.md)). Its `ArchitectureCheck` executable may import SwiftSyntax, SwiftParser and Foundation. Its `JSONEdit` executable, which edits the self-test's fixture `rules.json` so that the self-test needs only the Swift toolchain (#438), may import Foundation only.
- **`Tools/SourceChecks`**: the checks of source text, which read the repository and so cannot run in a test plan: the machines that run one have only the built products.
  - **What it checks:** the string catalog in its six languages and the keys the code uses (placeholders are compared by argument position, so `%@ has %lld items` and `%lld Elemente für %@` differ while `%2$lld Elemente für %1$@` matches; in the new app's views every string literal with words must be a key, a lookup, a listed non-key or the argument of a non-text parameter, wherever it stands, so a ternary, a local, a multiline literal or `Text("…".uppercased())` cannot show untranslated English; a literal nested in a value of another literal, at any depth, is checked on its own, and a lookup (`String(localized:)`, `LocalizedStringKey(`, `LocalizedStringResource(`, `.localized`) is exempt from that rule but its key must be in the catalog, whether its literal is plain, raw or multiline; every check reads the literals through one lexer, which skips comments (block comments nest) and reads a comment marker inside a literal as text; the legacy app keeps the scan of the literals handed straight to a view); the rules the app's views follow (accent colours, button presses, the list's delete button); how the tests render views off screen (with Core Graphics, never through the GPU image of an `ImageRenderer`); release hygiene (console output, the privacy manifest, the linked products); the deployment targets (the project and every package manifest set iOS 26.5 or later: the web view's content rules let `object` and `embed` loads through on iOS 26.2, so the minimum is not lowered without a defence that does not rely on them, #180). The project file is read for every build setting that sets a release, and a manifest (`Package.swift` and `Package@swift-X.Y.swift`, in any case: a Mac's volume does not tell them apart) from its tokens, for the `platforms:` of its `Package` call: a platform written in a comment or a string is none, and whatever the reader cannot tell (a platforms list that is a variable, a release that is not a string or a `.vNN_N` constant, a source that cannot be read to its end) is a finding, because it could hide any value; so is a folder the scan cannot list, and so is any link or other entry that is not a folder or a regular file, as the scan never follows a link nor looks up its target. The manifests of the folders in `DeploymentTargets.hostOnlyFolders` (`Tools/`) may declare no iOS platform, and the validation prototype is not read. `Tools/Release/check-archive.sh` checks the same minimum on the archive (`MinimumOSVersion`), and a test holds its constant to the one of this check. The documents are checked too, over the files git tracks: every Markdown file is in English (by the share of the function words of each of the app's languages in it; the translated sections of the store listing are the only text left out), every path in the README's "Where things are" table exists and every top-level folder is in it, and the open-source files (`LICENSE`, `NOTICE`, `CONTRIBUTING.md`, `SECURITY.md`, `CODE_OF_CONDUCT.md`) exist and are linked from the README. The licence notices the new app bundles (`PrestoCVNext/Resources/Licences.json`) say what the repository publishes: the app's own notice is the attribution of `NOTICE`, the Apache License is `LICENSE` (both with their whitespace normalised), and every notice names a licence the file holds once.
  - **Its target:** one test target, `SourceChecksTests`, which may import Testing and Foundation. It depends on no package, so it builds in seconds on Linux.
  - **Where it runs:** `swift test` runs it on the Linux CI job and, through `ci_scripts/ci_post_xcodebuild.sh`, on a maintainer's Mac (the pull request check) and on the Xcode Cloud build host (the Release workflow).
